# evals/ — Evaluation Harness

The base the workshop's evals plug into: it plays the dataset and records what the system did. The evaluators themselves are built during the workshop on top of the `RunRecord`s. Like `cli.py`, this layer is a composition root and may import from any other layer; nothing in `app/` imports from it.

## Dataset (`dataset.py`, `evals/dataset.json`)

The workshop's golden dataset: every eval, from the runner to the real-model unit tests and the judge, takes its inputs and expected values from it. One `EvalCase` per object of the JSON array in `evals/dataset.json` (pretty-printed so it reads well on screen in class): the user, the messages to play in order, and the references each technique needs — `expected_trip` (the trip the interpreter should extract from the first message, `budget_amount` included), `required_agents` (which orchestrator tools must run on the first message), `user_preferences` (LLM-as-a-Judge rubric input), `confirmation_message_index` and `max_lodging_total` (booking risk), `reference_answer` (similarity) and `itinerary_brief` (the facts the orchestrator would hand the output generator, so the generator can be tested alone). A case without `reference_answer` or `itinerary_brief` is one whose good answer is a question, not an itinerary (`ana-paraty-sem-orcamento`); the tests that need those fields skip it.

Dates are **placeholders** (`{next_saturday}`, `{next_saturday_br}`, `{saturday_in_5_weeks}`, …) resolved by `load_dataset(path, today)`, because the weather forecast only covers ~16 days ahead. Every `RunRecord` stores its resolved case, so evaluating old results never re-resolves dates.

Keep the cases tied to the seed: user ids and catalog cities come from `app/data/seed.sql`. The budget is never stored, so a case states it in its messages, like a user would; `max_lodging_total` is the lodging limit that case states. Keep `itinerary_brief` and `reference_answer` telling the same trip, since the similarity tests compare the generator's output from one against the other.

`evals/golden.py` loads it for the evals outside `app/`: `golden_cases()` (dates resolved against today) and `golden_case(id)`.

## Runner (`runner.py`, `records.py`)

`run_case` plays one case against the orchestrator on a **freshly seeded throwaway database** (runs never see each other's reservations) and returns a `RunRecord`: per turn, the response, each delegation to a specialist (`AgentCall`), reservations created, trace id, latency, and any model API error or turn over the token budget (either ends that run instead of the whole dataset). Between turns it carries the history the same way as the CLI (`next_turn_history`: the latest turn in full, earlier ones as text only). Traces are tagged `dataset` + the case id in Langfuse.

`make run-dataset RUNS=3 CASES=id1,id2` runs it against the real API and writes `evals/runs/<timestamp>/results.json` (git-ignored), an indented JSON array like the dataset, rewritten after every run (`save_run_records` / `load_run_records` in `records.py`). Each run makes a dozen or more model calls — narrow with `CASES` while iterating.

## Real-model unit tests (`evals/unit_tests/`)

pytest tests that call the **real model** — the workshop's checks on an agent's output (a regex over a reply, validating a structured response against its model) — live in `evals/unit_tests/`, never in `tests/`. `tests/` loads `test.env` and never calls the model; `evals/unit_tests/conftest.py` uses `.env` as-is, and pyproject's `testpaths = ["tests"]` keeps `make test` / `make test-ci` (and CI) from ever collecting them. Never run both directories in the same pytest invocation: whichever conftest loads first decides the configuration the app is built with.

- **No real key, no run.** The conftest checks `MODEL_API_KEY` (shell or `.env`) before anything under `app/` is imported; when it is missing or still a placeholder (`changethis`, `test`), every file there is skipped without being imported and the reason is printed. The check is `missing_model_api_key_reason` in `evals/unit_tests/model_api_key.py`, unit-tested in `tests/evals/`.
- **Fixtures:** `connection` (a freshly seeded throwaway SQLite file per test, as in `tests/`), `model_client` (a real `ModelClient()`), and `runs` (the `RUNS` environment variable, default 3).
- **Tracing** follows `.env`: each test is one Langfuse trace tagged `unit-test` (`unit_test_trace` in `evals/unit_tests/tracing.py`), flushed when the session ends. With `LANGFUSE_TRACING_ENABLED=false` nothing is sent. There is no per-test token budget, since a test repeating a turn `runs` times would exceed the per-turn one.
- **Every test runs on the golden dataset.** A module-scoped `case` fixture is parametrized over `golden_cases()`, filtered to the cases that carry what the test needs, so pytest reports one result per case and the agent's input and the expected values both come from the case.
- **Generate once per file and case.** When several tests check the same agent output, a module-scoped fixture produces it `runs` times per case and every test in the file reuses it, so the file costs `runs` model calls per case instead of `runs` per test (see `itineraries` in `test_itinerary_format.py`). Such a fixture runs before the per-test trace exists, so it builds its own `ModelClient()` and wraps its body in `unit_test_trace(__name__)` to keep its calls tagged. It makes the `runs` calls at once with `run_in_parallel` (`evals/unit_tests/parallel.py`), so a `RUNS=10` file waits for the slowest call instead of ten in a row (the word-limit test went from about 5 minutes to under 1).
- `test_environment.py` is the students' setup check (`make check-env`): one real model call, then a trace it polls for on Langfuse Cloud through the v2 observations API, since organizations created from September 2026 on no longer have the legacy `GET /traces/{id}`.
- `make test-model` runs them (`RUNS=5`, `TEST_PATH=evals/unit_tests/test_x.py`, `ARGS="-s -k name"`).
- **End to end:** `test_end_to_end.py` evaluates the whole system from a `make run-dataset` results file (the latest under `evals/runs/`, or `RESULTS=…`; skipped when there is none), one result per case across its runs: required agents on the first message, no booking before the confirmation message, bookings within `max_lodging_total` and matching `expected_trip` (exact checks, no model call), then similarity to `reference_answer` and an LLM judge on `user_preferences`. The judge gets the user's messages and the reservations made (with each lodging's catalog kind) and scores each preference on its own, marking the ones the answer cannot address yet; the run's score is the mean of the applicable ones. The answer they grade is the turn that called `generate_itinerary`, since the last turn may only confirm a booking. `make eval-end-to-end` runs just this file.
- **The word-limit test** (`test_itinerary_length.py`) is the pass@k activity: its pass criterion is `pass^K >= MIN_PASS_HAT_K` rather than every run passing, and it prints pass@K and pass^K per case (`ARGS="-s"`).

Every test costs tokens and its result varies from run to run: repeat a stochastic check `runs` times and assert a pass rate against a threshold rather than a single outcome, and narrow with `TEST_PATH` / `-k` while iterating.

`pass_metrics.py` has the estimators those repeated runs report: `pass_at_k(n, c, k)` (Chen et al. 2021, at least one of `k` runs passes) and `pass_hat_k(n, c, k)` (Yao et al. 2024, τ-bench, all `k` pass), for `c` passing runs out of `n`. Each base test in `evals/unit_tests/` keeps its own pass criterion and puts pass@1 and pass^n in its failure message; the estimators are unit-tested in `tests/evals/`.

## LLM-as-a-judge evals (`evals/judge/`)

Open-ended answers whose quality depends on the request (does the research agent respect the user's preferences?) are graded by a second model with a rubric, through [promptfoo](https://www.promptfoo.dev/), a Node CLI pinned in the root `package.json` (`make install-judge`, separate from `make install` so CI and the Python setup never need Node). The pinned version needs Node 22.22+.

- `promptfooconfig.yaml` runs the research agent through `research_agent_provider.py`, a promptfoo Python provider (`call_api`) that builds the agent with a real `ModelClient()`. Each test's prompt is a case id (`vars.caso`); the provider sends that case's first message to the agent, so the rubrics in the YAML grade answers to the golden dataset. It is a composition root like the runner: one Langfuse trace tagged `llm-judge` per call, its own prompt cache key and token budget, flushed before returning since promptfoo may end the worker right after.
- `judge_consistency.yaml` grades hand-written fixed responses to the `carla-paraty-confirma-reserva` case through promptfoo's `echo` provider, so only the judge varies — the base for checking the judge's own consistency and agreement with human labels.
- The grader is `openai:chat:gpt-6-luna` with `apiKeyEnvar: MODEL_API_KEY`. promptfoo doesn't know gpt-6-luna is a reasoning model, so `reasoning_effort: none` goes through `passthrough`, and `omitDefaults` drops the `max_tokens` it would send otherwise (the model only accepts `max_completion_tokens`). The model name is fixed in the YAML: changing `MODEL` or `MODEL_BASE_URL` in `.env` does not move the judge.
- `make eval-judge` (`CONFIG=…`, `ARGS="--repeat 3"`) runs from the repo root, so promptfoo and the app both read `.env`; it sets `PROMPTFOO_PYTHON` to the repo's `.venv` and `PYTHONPATH` to the root so `app` imports, disables promptfoo's telemetry and update check, passes `--no-cache` (a cached answer would hide the variation the workshop measures), and keeps promptfoo's results database in `.promptfoo/` (git-ignored). `make view-judge` opens it.
- promptfoo reads `LOG_LEVEL` too and prints nothing when it is uppercase, so the make targets pass `info`; the app's `Settings` uppercases `LOG_LEVEL`, so the provider still builds.
